# WatchPlay 协议 v0.1 — 总览

> 状态：**Draft**（协议版本 `0.1`）
> 本组文档是 WatchPlay 手机 ↔ 手表投屏协议的**规范性定义**。实现必须遵循 `MUST` / `MUST NOT`（必须/禁止）、`SHOULD`（应当）、`MAY`（可选）的约定，术语含义见 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)。

## 1. 它解决什么问题

手机 App 用 **HTML + CSS** 渲染一个专为手表屏幕设计的 UI，经 WebView 渲染后编码为 **JPEG（MJPEG）或 H.264**，通过蓝牙发送到手表解码显示；手表的触控通过 BLE 回传手机，形成交互闭环。

```
┌────────────────────────── 手机 (Android) ──────────────────────────┐
│  HTML+CSS 手表 UI                                                  │
│      │ WebView                                                     │
│      ▼                                                             │
│  OpenGL 绘制到纹理 ──► MediaCodec 编码 ──► 协议封装 ──► 传输层      │
│      ▲                                                    │        │
│      │ 更新画面                                    BLE GATT / CoC  │
│  触控映射 ◄── 协议解包 ◄──────────────────────────────────┼────────┤
└───────────────────────────────────────────────────────────┼────────┘
                                                            │
┌────────────────────────── 手表 (ESP32-S3 等) ──────────────┼────────┐
│  传输层 ──► 协议解包 ──► 解码 (JPEG硬解/H.264) ──► PSRAM 双缓冲 ──► 圆屏 │
│                                                   │                │
│                              触控采集 (FT3168 等) ─┘                │
└────────────────────────────────────────────────────────────────────┘
```

### 与"屏幕录制投屏"的区别

| | 传统投屏（MediaProjection） | WatchPlay |
| :--- | :--- | :--- |
| 画面来源 | 整块手机屏幕 | App 自己渲染的手表 UI 场景 |
| 权限 | 需要录屏授权弹窗，属敏感权限 | **不需要**任何录屏/隐私权限 |
| 分辨率 | 手机原生（需缩放） | 直接按手表分辨率渲染，1:1 像素 |
| 交互 | 只能看，或反向投屏 | 触控回传，闭环交互 |
| 应用场景 | 任意手机内容 | 为手表**专门设计**的导航/音乐等界面 |

**核心洞察**：手表屏幕小、所以 UI 简单；UI 简单、所以才可以用 HTML+CSS 描述；用 HTML+CSS 描述、所以可以 1:1 按手表分辨率渲染而无需缩放录制整块手机屏。这消除了 90% 的带宽和权限问题。

## 2. 设计目标（v0.1）

| 目标 | 指标 |
| :--- | :--- |
| 端到端延迟 | < 200 ms（MJPEG @ 10 fps，参考硬件） |
| 码率 | Profile A: 150–300 KB/s；Profile B: 200–800 kbps |
| 首帧时间 | < 500 ms（连接建立到首帧显示） |
| 内存占用（手表） | 帧头层承载缓冲 `2 × (16 + max_chunk_bytes)` = **520 字节**；视频层整帧重组缓冲由 `max_frame_bytes` 决定（参考值 < 2 MB）；1 帧解码缓冲 |
| 芯片要求（Profile A） | 任意带 JPEG 硬解 + BLE 或 BR/EDR 的 MCU |
| 协议开销 | 每帧 ≤ 0.3%（不含传输层分片头） |

### 为什么是这两个 Profile

| Profile | 适用芯片 | 编码 | 手表端解码 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| **A: MJPEG** | 任意带 JPEG 硬解的低端 MCU | 手机端按需压 JPEG | JPEG 硬解，可到 10–15 fps | **基线，必须支持** |
| **B: H.264** | 带 H.264 硬解的中高端芯片 | MediaCodec Baseline | 硬解，15–30 fps | 带宽友好；软解芯片（如 ESP32-S3）达不到 10 fps，协商时不会被选中 |

A 是基线：不需要 H.264 硬解，随机丢帧只影响那一帧。B 的价值在带宽（200–800 kbps 对 1.2–2.4 Mbps），代价是必须硬解，且丢帧要等下一个 IDR 才能恢复。

参考实现（一块 ESP32-S3 板）只能软解 H.264，所以它落在 A 上——这是那一块板的约束，不是协议的偏向。带 H.264 硬解的芯片（如 ATS3089）应当用 B。

## 4. 术语表

| 术语 | 含义 |
| :--- | :--- |
| **发送端 / Source** | 手机侧，产生并编码画面 |
| **接收端 / Sink** | 手表侧，解码并显示画面 |
| **场景 / Scene** | 一份 HTML+CSS 文档，描述一个手表 UI 界面 |
| **帧 / Frame** | 一个完整的可独立解码的画面（一帧 JPEG 或一个 H.264 Access Unit） |
| **分块 / Chunk** | 一帧被切分后的传输单元，一帧 = N 个分块 |
| **Credit** | 接收端授予发送端的发送许可，单位是"分块" |
| **安全区 / Safe Area** | 圆屏上不会被切掉、且视觉舒适的内接矩形区域 |
| **能力 / Capabilities** | 接收端上报的硬件与解码能力集合 |
| **Profile** | 编码档位（A: MJPEG / B: H.264） |

## 5. 一致性

一个实现声称"支持 WatchPlay 协议 v0.1"时：

- **必须（MUST）** 正确实现 [02-wire-format.md](02-wire-format.md) 的帧头解析与 **CRC-16/CCITT-FALSE** 校验。
- **必须（MUST）** 实现 [03-session.md](03-session.md) 的握手与能力协商，并在协商失败时干净地断开。
- **必须（MUST）** 支持 [04-video.md](04-video.md) 的 Profile A（MJPEG）。
- **应当（SHOULD）** 支持 [05-input.md](05-input.md) 的触控回传（纯显示设备可豁免，须在能力位中声明）。
- **可以（MAY）** 支持 Profile B、Wi-Fi 承载、经典蓝牙承载（[01-transport.md §5](01-transport.md)）、音频旁路。
