# 07 — 能力体系（Capabilities）

本文件是 WatchPlay v0.1 **能力位、TLV 注册表、扩展与版本兼容规则的权威索引**。

TLV 的字节布局定义在 [03-session.md §3](03-session.md)。本文件**不重复**那些字节表，而是负责：① 作为唯一注册表，避免编号冲突；② 定义扩展与兼容规则；③ 给出实现矩阵。

> **编号冲突是协议腐化的头号原因。** 任何新增 `TLV type`、`CONTROL opcode`、`BYE reason`、`FrameType`、`Flags` 位之前，**必须（MUST）** 先在本文件登记。未登记的编号视为无效。

### 1.1 厂商私有空间的纪律

厂商 **禁止（MUST NOT）** 在标准空间内定义语义。厂商扩展 **必须（MUST）**：

- 使用对应的 `0x80`–`0xFF` 范围。
- 随帧置 `flags` 的 `VENDOR` 位（`0x8000`）——**唯一例外**是 `CAPS` TLV，因为它没有独立的 flags。
- 在厂商文档中说明其编号的**有效期**。厂商 **应当（SHOULD）** 把编号视为临时占用，一旦上游标准化就迁移过去。

接收方遇到任何 `VENDOR` 标记的内容，**必须（MUST）** 按长度跳过，**禁止（MUST NOT）** 因为不理解而断开或报错。

## 2. `CAPS` TLV 注册表

方向约定：**↓ = 手表→手机（`CAPS`）**，**↑ = 手机→手表（`CAPS_ACK`）**。

| `type` | 名称 | 方向 | `len` | 必需性 | 定义 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `0x01` | `DEVICE_INFO` | ↓ | 16 | **必须** | [03 §3.2](03-session.md) |
| `0x02` | `DISPLAY` | ↓ | 16 | 有屏时**必须** | [03 §3.3](03-session.md) |
| `0x03` | `CODEC_MJPEG` | ↓ | 4 | 与 `0x04` 至少一个 | [03 §3.4](03-session.md) |
| `0x04` | `CODEC_H264` | ↓ | 8 | 与 `0x03` 至少一个 | [03 §3.5](03-session.md) |
| `0x05` | `INPUT` | ↓ | 4 | 有触控时**应当** | [03 §3.6](03-session.md) |
| `0x06` | `AUDIO` | ↓ | 4 | 可选 | [03 §3.7](03-session.md) |
| `0x07` | `MEMORY` | ↓ | 8 | 可选（**强烈建议**） | [03 §3.8](03-session.md) |
| `0x08` | `POWER` | ↓ | 4 | 可选 | 本文件 §2.1 |
| `0x09` | `TRANSPORT` | ↓ | 变长 | 可选 | 本文件 §2.2 |
| `0x0A` | `SENSORS` | ↓ | 4 | 可选 | 本文件 §2.3 |
| `0x0B`–`0x7F` | *保留* | — | — | 未来标准 | — |
| `0x80`–`0xFF` | *厂商私有* | — | — | 可选 | — |

`CAPS_ACK` 侧的 TLV：

| `type` | 名称 | 方向 | `len` | 必需性 | 定义 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `0x01` | `RESULT` | ↑ | 24 | **必须** | [03 §4](03-session.md) |
| `0x02` | `STREAM` | ↑ | 12 | **必须** | [03 §4.1](03-session.md) |
| `0x03` | `REJECT_REASON` | ↑ | 变长 | 失败时**必须** | [03 §3.9](03-session.md) |

> **注意编号在不同方向上有不同含义。** `CAPS` 的 `0x01` 是 `DEVICE_INFO`，`CAPS_ACK` 的 `0x01` 是 `RESULT`。这是刻意的：两个方向的 TLV 集合互不相交（`CAPS` 全在上表前半，`CAPS_ACK` 全在下表），解析器只需知道自己期望哪个方向，无需为同一编号做歧义判断。**实现时必须按方向选择解析表。**

### 2.1 `POWER`（4 字节）

| 偏移 | 长度 | 字段 | 类型 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| 0 | 1 | `battery_percent` | u8 | `0`–`100`，`0xFF` = 未知 |
| 1 | 1 | `charging` | u8 | `0` = 放电，`1` = 充电中 |
| 2 | 1 | `thermal_state` | u8 | `0` = 正常，`1` = 温，`2` = 热，`3` = 危急 |
| 3 | 1 | `power_profile` | u8 | `0` = 性能优先，`1` = 均衡，`2` = 省电 |

手机 **应当（SHOULD）** 据此调整：

| 条件 | 动作 |
| :--- | :--- |
| `battery_percent < 15` 且未充电 | 帧率降至 ≤ 5，并在 UI 提示 |
| `thermal_state >= 2` | 帧率 −30%，质量 −10 |
| `power_profile == 2`（省电） | 帧率上限 5，质量上限 60 |

### 2.2 `TRANSPORT`（变长）

一个位图 + 可选参数，声明本设备支持的承载。

| 偏移 | 长度 | 字段 | 类型 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| 0 | 1 | `bearers` | u8 | bit0=GATT，bit1=L2CAP CoC，bit2=Wi-Fi TCP，bit3=经典蓝牙 SPP（[01-transport.md §5](01-transport.md)） |
| 1 | 1 | `preferred` | u8 | 首选承载的位值（如 `0x02`） |
| 2 | 1 | `mtu` | u8 | **上限截断为 255** 的可用负载字节数；更大时用扩展 TLV |
| 3 | 1 | `reserved` | u8 | |
| 4 | … | `ext` | 变长 | 可选。当 bit3 置位时，前 2 字节 **必须（MUST）** 是 u16 小端的 `bearer_tu`（它的值超过 u8 的 `mtu` 上限，见 [01-transport.md §5.2](01-transport.md)）；其余为 Wi-Fi SSID/PSM 等自定义内容 |

### 2.3 `SENSORS`（4 字节）

| 偏移 | 长度 | 字段 | 类型 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| 0 | 1 | `accelerometer` | u8 | `0` = 无，`1` = 有 |
| 1 | 1 | `gyroscope` | u8 | |
| 2 | 1 | `heart_rate` | u8 | |
| 3 | 1 | `compass` | u8 | |

> **这些传感器数据不在 v0.1 协议范围内。** `SENSORS` TLV 只声明**存在性**，让手机知道可以请求（通过厂商私有 `CONTROL` opcode）。理由：传感器回传的采样率需求（心率 1 Hz vs 加速度计 50 Hz）差异极大，把它们塞进 v0.1 会过早固化设计。见 §5 开放问题。

## 3. 必需性与降级

### 3.1 手表侧发送 `CAPS` 的最低要求

一个 `CAPS` **必须（MUST）** 至少包含：

1. `DEVICE_INFO`（`0x01`）
2. `DISPLAY`（`0x02`）——纯音频设备可省略，但 v0.1 无此类产品
3. `CODEC_MJPEG`（`0x03`）**或** `CODEC_H264`（`0x04`）

缺少以上任何一项 → 手机 **必须（MUST）** 回 `RESULT.status = CAPS_MALFORMED`。

### 3.2 手机侧发送 `CAPS_ACK` 的最低要求

1. `RESULT`（`0x01`）
2. `STREAM`（`0x02`）

缺少任何一项 → 手表 **必须（MUST）** 发 `BYE(PROTOCOL_ERROR)` 并断开。

### 3.2.1 承载层的硬下限：MTU ≥ 100

协商结果不仅要满足 §3.1 的结构要求，还必须满足**可传输性**：由 `max_chunk_bytes = MTU − 16` 与下限 `max_chunk_bytes ≥ 84` 反解得 **`MTU ≥ 100`**。

- `MTU < 100`（例如未协商的默认 23）时，手机 **必须（MUST）** 返回 `RESULT.status = BANDWIDTH_INSUFFICIENT`，**禁止（MUST NOT）** 把 `max_chunk_bytes` 抬到下限硬撑——84 字节的负载装不进 20 字节的 ATT 单元。
- 手表的 `CODEC_*` 能力申报 **禁止（MUST NOT）** 依赖手机一定能协商到足够的 MTU；它应当在收到 `CAPS_ACK` 之前按最保守的假设工作。
- 完整推导与参考实现做法见 [03-session.md §4.2](03-session.md) 与 [01-transport.md §2.2](01-transport.md)。

> 这条下限是一个实用的"快速失败"：拿不到 ≥ 100 的 MTU 说明对端协议栈有问题。此时明确报错远优于继续推流——后者表现为每帧 `chunk_total` 不符、画面残缺，而日志里没有任何线索。

### 3.3 降级顺序

当手机无法满足手表的最佳能力时，**必须（MUST）** 按此顺序降级（前面的优先被牺牲是**错误**的，越靠上越先被保住）：

1. **保住可解码性**（codec 必须是手表明确声明的）
2. **保住分辨率**（不做非整数缩放；宁降帧率也不改分辨率）
3. **降帧率**（`target_fps` 逐级下调）
4. **降质量/码率**
5. **最后** 才考虑降分辨率（此时必须在 `RESULT.width/height` 中如实声明）

> **为什么分辨率排在帧率前面**：非整数缩放会让文字渲染糊掉，而手表 UI 的价值主要在文字（导航转向、歌名）。降帧率只是让动画变卡，降分辨率会让内容读不清。这是一个明确的产品判断。

## 4. 版本兼容规则

### 4.1 向前兼容（新实现读旧数据）

新实现 **必须（MUST）** 能完整处理旧版本发出的所有帧，做法是**只依赖本文件登记的字段**，并且在字段取值超出已知范围时**有定义的退化行为**。

**禁止（MUST NOT）** 因为枚举取值未识别而失败。例如 `DISPLAY.shape = 3`（圆角矩形，未来新增）在 v0.1 实现中 **应当（SHOULD）** 按方形处理并记录一条警告。

### 4.2 向后兼容（旧实现读新数据）

旧实现 **必须（MUST）** 通过以下机制安全忽略新内容：

| 新内容 | 安全忽略的机制 |
| :--- | :--- |
| 新 `FrameType` | 按 `hdr_len`/`payload_len` 跳过；见 [02 §3](02-wire-format.md) |
| 新 `CAPS` TLV | 按 TLV 的 `len` 跳过 |
| 更大的 `hdr_len` | 跳过 `hdr_len - 16` 字节扩展区；见 [02 §1.1](02-wire-format.md) |
| 新 `flags` 位 | 位是"置位才有意义"的；未知位 **必须** 被忽略 |
| 新 `CONTROL opcode` | 忽略，并 **应当（SHOULD）** 回 `ACK`（若置了 `ACK_REQUIRED`） |
| 新 `BYE reason` | 记录日志，按通用错误处理 |
| 新 `RESULT.status` | 视为失败，断开 |

### 4.3 版本号递增的判据

| 变更类型 | 所需的版本变更 |
| :--- | :--- |
| 新增可选 TLV / opcode / 厂商扩展 | **不增加**版本号（向前兼容） |
| 新增必需 TLV | 次版本 +1（如 `1.1`），并同时提供旧路径 |
| 修改已有字段的语义或长度 | **主版本 +1**，必须同时提供兼容读路径 |
| 修改帧头布局 | **主版本 +1**，且 `HELLO.min_version` 必须反映 |

> v0.1 期间（`version = 1`），[02-wire-format.md §9](02-wire-format.md) 明确禁止变更帧头布局。因此在 1.0 之前，任何需要改帧头的想法都 **必须** 被转化为 TLV 扩展或推迟到 1.0。

## 5. 开放问题（v0.2 候选）

| 议题 | 说明 | 倾向 |
| :--- | :--- | :--- |
| 传感器数据通道 | 是否需要定义标准的心率/加速度计回传 TLV | 倾向定义，但独立的可选 TLV，不放进 `CAPS` |
| 多场景（多窗口） | 手机同时推多个"场景"（如主界面 + 通知气泡） | 倾向用 `FrameType` 的厂商段先在参考实现中试验 |
| 帧级时间戳的标准化 | 目前 `V_TS_PRESENT` 是可选（[04 §2.3](04-video.md)） | 倾向在 v0.2 改为**必须**，因为它对端到端延迟的可观测性是唯一手段 |
| `CAPS` 的双向性 | 目前 `CAPS` 单向（手表→手机），手机的能力只在 `HELLO_ACK.flags` 里粗略声明 | 倾向新增 `CAPS_SOURCE` TLV |
| 音频旁路 | 支持经典蓝牙的芯片（ATS3089）如何建立 A2DP 链路 | 倾向定义 `CONTROL(SWITCH_TRANSPORT, A2DP)` 但不在 v0.1 实现 |
| 传输切换的原子性 | `SWITCH_TRANSPORT` 过程中的丢帧边界未定义 | 见 [01-transport.md](01-transport.md) 开放问题 |
| 经典蓝牙承载的配对与取舍 | 只有 BR/EDR 的设备如何配对、`bearer_tu` 取多少、双模设备选哪个承载 | 见 [01-transport.md §11](01-transport.md) 的 Q12–Q14 |
| TLV 长度扩展 | `len` 是 u8，上限 255 字节，`CAPS` 总预算 128 字节 | 倾向把 `CAPS` 上限提到 256 并让 `len` 用 u8 但允许跨 TLV 分片 |

## 7. 新增能力的流程

任何想扩展协议的贡献者 **必须**：

1. 在本文件登记编号（TLV / opcode / flag 位）。
2. 说明**为什么**现有的扩展点不够用（多数需求可以落在厂商私有空间里先验证）。
3. 提供向前/向后兼容的分析（按 §4.2 的表逐项检查）。
4. 更新 [99-changelog.md](99-changelog.md)。
5. 在 `tools/` 的参考实现中加入编码/解码路径，并在 `examples/protocol-traces/` 里加入一个 trace。

## 8. 一致性检查清单

- [ ] 所有使用的 TLV `type` 都在本文件登记
- [ ] `CAPS` 按方向选择解析表（`CAPS` vs `CAPS_ACK`）
- [ ] 未知 TLV 按 `len` 跳过而非报错
- [ ] 未知枚举值有定义的退化行为，不崩溃
- [ ] 未知 `flags` 位被忽略
- [ ] `hdr_len > 16` 时跳过扩展区
- [ ] 厂商扩展使用 `0x80`–`0xFF` 且置 `VENDOR`
- [ ] `CAPS` 含 `DEVICE_INFO` + `DISPLAY` + 至少一个 `CODEC_*`
- [ ] `CAPS_ACK` 含 `RESULT` + `STREAM`
- [ ] 降级顺序遵循 §3.3（分辨率优先于帧率保留）
- [ ] 协议变更已更新本文件与 changelog
